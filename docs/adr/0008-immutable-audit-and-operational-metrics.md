# ADR 0008: Неизменяемый аудит и операционные метрики

- Статус: принято
- Дата: 2026-08-17

## Контекст

OrderFlow выполняет конкурентные складские и платёжные операции, поэтому одних прикладных логов
недостаточно для ответа на вопросы «кто изменил объект» и «какое событие привело к состоянию».
Логи также не подходят для долговременной истории: они могут ротироваться, дублироваться и не
имеют ограничений неизменяемости. Для эксплуатации нужны отдельные числовые сигналы о HTTP и
очереди событий.

## Решение

Успешно доставленное доменное событие создаёт `inbox_events` и `audit_events` одним commit.
`source_event_id` уникален, а Inbox блокирует повторную обработку. PostgreSQL-trigger запрещает
`UPDATE` и `DELETE` аудита даже при ошибке прикладного кода.

Аудит не копирует произвольный payload. Для каждого типа события задан whitelist безопасных
деталей; actor, resource и `correlation_id` хранятся отдельными колонками. Чтение доступно только
текущему `admin` и поддерживает ограниченную пагинацию и индексированные фильтры.

API публикует `/metrics` в Prometheus format. HTTP-счётчики и histogram latency хранятся в процессе,
а Outbox gauges и сумма попыток вычисляются из PostgreSQL при scrape. Маршруты, а не реальные
идентификаторы, используются как labels. Отдельный Compose profile запускает Prometheus.

## Последствия

- повтор события не создаёт повтор аудита;
- история защищена от обычного изменения и удаления на уровне БД;
- секреты не попадают в аудит только потому, что появились в новом payload;
- администратор может искать связанные операции по `correlation_id`;
- HTTP-метрики сбрасываются при перезапуске процесса;
- Outbox-метрики отражают сохранённое состояние между перезапусками;
- `/metrics` не содержит бизнес-идентификаторов, но в production требует сетевого ограничения.
