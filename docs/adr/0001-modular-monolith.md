# ADR 0001: модульный монолит как основная архитектура

- Статус: принято
- Дата: 2026-08-10

## Контекст

OrderFlow содержит несколько связанных областей: пользователей, каталог, склады, заказы, платежи, аудит и аналитику. Микросервисы дали бы независимое масштабирование, но потребовали бы распределённых транзакций, отдельного деплоя, сетевой диагностики и поддержки нескольких хранилищ. Для pet-проекта это ухудшило бы надёжность и замедлило проверку главных бизнес-правил.

Обычный монолит без границ проще запустить, но со временем превращает маршруты, модели и запросы в тесно связанный код.

## Решение

Использовать модульный монолит:

- один FastAPI-процесс и одна основная PostgreSQL;
- отдельные пакеты по бизнес-областям;
- публичные сервисы для синхронного взаимодействия модулей;
- доменные события и Outbox для асинхронной реакции;
- транзакция управляется сценарием использования, а не HTTP-маршрутом.

## Последствия

Плюсы:

- простая локальная разработка и облачный деплой;
- ACID-транзакции для заказа и резервов;
- бизнес-модули можно тестировать изолированно;
- при реальной необходимости модуль проще выделить в сервис.

Ограничения:

- модули пока не масштабируются независимо;
- границы поддерживаются правилами кода и ревью, а не сетью;
- изменения общей базы требуют согласованных миграций.
