# ADR 0009: Операционная аналитика и Redis cache-aside

- Статус: принято
- Дата: 2026-08-17

## Контекст

Менеджеру нужны сводка продаж, топ товаров и низкие доступные остатки. Текущие статусы платежа и
заказа недостаточны для истории: после возврата успешный платёж становится `refunded`, но факт
первичной оплаты должен остаться в gross revenue. Создавать отдельное хранилище проекций для
небольшого pet-проекта пока неоправданно.

## Решение

Отчёты продаж используют неизменяемые Outbox-события как бизнес-факты и ограничивают их по
`created_at`. Суммы агрегируются по валюте и дню. Net revenue вычисляется как gross успешных оплат
минус сумма возвратов. Топ товаров связывает единственное событие `payment.succeeded` с платежом и
снимками `order_items`. Низкие остатки читаются из актуальных `stock_balances` только для активных
товаров и складов.

API доступен ролям `manager` и `admin`, по умолчанию использует последние 30 дней и запрещает
периоды длиннее 366 дней. Индекс Outbox `(event_type, created_at)` поддерживает основные временные
выборки.

Результат кешируется в Redis по схеме cache-aside на короткий настраиваемый TTL. Все параметры и
версия контракта входят в ключ. Ошибки Redis и невалидные значения кеша не влияют на доступность:
сервис повторно строит отчёт из PostgreSQL и лишь логирует тип ошибки кеша.

## Последствия

- gross и refunds сохраняют отдельный исторический смысл;
- разные валюты никогда не суммируются между собой;
- аналитика не дублирует бизнес-данные и не требует отдельного consumer;
- отчёты отражают committed Outbox-события независимо от их статуса доставки;
- повторные запросы уменьшают нагрузку на PostgreSQL в пределах TTL;
- данные могут быть устаревшими не более чем на TTL;
- при росте объёма событий запросы можно заменить проекциями без изменения HTTP-контрактов.
